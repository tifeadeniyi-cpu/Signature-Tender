# Threat model (STRIDE)

Living document. Each later phase adds its own section.

| Category               | Threat                                    | Control in place                                                                                                               | Test                                              |
| ---------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| Spoofing               | Credential stuffing or brute force        | Rate limits on sign-in, sign-up, reset and TOTP; 12-char passwords; breached-password check (staging/prod); TOTP MFA; passkeys | Manual; rate limit is config-tested in staging    |
| Spoofing               | Unverified email used to act as someone   | Sign-in refused until email verified                                                                                           | e2e: unverified sign-in redirects to verification |
| Tampering              | Changing another workspace via forged ids | RLS policies + service permission checks                                                                                       | `tenant-isolation.test.ts`                        |
| Tampering              | Forged workspace-switch cookie            | Membership re-checked on every request                                                                                         | Service test (forbidden on non-member)            |
| Repudiation            | Denying a settings change                 | `audit_events` written in the same transaction; app role cannot update or delete                                               | `tenant-isolation.test.ts` (append-only)          |
| Information disclosure | Reading other tenants' data               | RLS with FORCE; app role has no BYPASSRLS; nothing visible without an actor                                                    | `tenant-isolation.test.ts`                        |
| Information disclosure | Account enumeration via reset             | Identical response whether or not the account exists                                                                           | Manual                                            |
| Information disclosure | XSS / clickjacking                        | React escaping, CSP, X-Frame-Options DENY, frame-ancestors 'none'                                                              | Headers set in `next.config.ts`                   |
| Denial of service      | Auth endpoint flooding                    | Database-backed rate limits                                                                                                    | Staging                                           |
| Elevation of privilege | Editor changing workspace settings        | `workspace.manage` required in service and RLS                                                                                 | Service + RLS tests                               |

## Phase 3: signing links and evidence

| Category               | Threat                                     | Control in place                                                                                                                                     | Test                                                |
| ---------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Spoofing               | Guessing or forging a signing link         | 256-bit random tokens; only a SHA-256 hash is stored; links expire; rotated when re-sent; invalidated on cancel                                      | `signing.test.ts` (unknown/malformed links, cancel) |
| Spoofing               | Forwarded link used by someone else        | Optional one-time email code: 6 digits, 10-minute expiry, single use, 5 attempts, 5 sends, 30 s resend gap; browser session bound by httpOnly cookie | `signing.test.ts`, `signing.spec.ts`                |
| Tampering              | Document changed after sending             | Source SHA-256 snapshotted on send and re-verified on every signer completion and at finalization; drafts frozen once sent                           | `signing.test.ts`                                   |
| Tampering              | Editing or deleting evidence               | `signing_events` is append-only for the app role and hash-chained; integrity check recomputes the chain and file hashes                              | `signing.test.ts` (tamper detection)                |
| Tampering              | Signer filling another signer's fields     | RLS: only `recipient_id = st_current_signer()` can update a field                                                                                    | `signing.test.ts`                                   |
| Repudiation            | Signer denies signing                      | Consent with disclosure version and hash, adoption method and image hash, explicit intent, IP and browser, all in the chain and certificate          | `signing.test.ts`                                   |
| Information disclosure | Signer browsing other data                 | Signer context sees only its own request and document; no workspace rows                                                                             | `signing.test.ts` (RLS scope)                       |
| Information disclosure | Token leaking via Referer, cache or search | `Referrer-Policy: no-referrer`, `no-store` and `noindex` on `/sign` and `/api/sign`                                                                  | Headers in `next.config.ts`                         |
| Information disclosure | Metadata in uploaded signature images      | Client redraws to PNG; server keeps only drawing chunks and proves the image decodes                                                                 | `signing.test.ts`                                   |
| Denial of service      | Double submit or race on completion        | Row locks, status checks and a unique open-request index; finalization is idempotent                                                                 | `signing.test.ts`                                   |
| Elevation of privilege | Sending without permission                 | `documents.send` required in service and RLS                                                                                                         | `signing.test.ts` (viewer refused)                  |

## Phase 4: payments and credits

| Category               | Threat                                           | Control in place                                                                                                                                                                       | Test                                     |
| ---------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Spoofing               | Forged "payment succeeded" (redirect or webhook) | The return page only reads our records. Credits are granted only from webhook events whose Stripe signature verifies with the endpoint secret                                          | `billing.spec.ts` (unsigned and forged)  |
| Tampering              | Paying less than the price                       | Amount and currency are fixed in a `payments` row from database prices before checkout; the webhook grants nothing unless Stripe's subtotal and currency match                         | `billing.test.ts` (amount mismatch)      |
| Tampering              | Minting credits through the app                  | The ledger is append-only (no UPDATE/DELETE grant). Signed-in users may only move one credit into or out of a hold for a request they can send; grants need the billing system context | `billing.test.ts` (forged grant refused) |
| Repudiation            | Disputed balance                                 | Every movement is a ledger row with source (payment, request), idempotency key and author; reconciliation compares paid payments with granted credits                                  | `billing.test.ts` (reconcile)            |
| Information disclosure | Card data                                        | Card entry happens on Stripe Checkout and the Stripe portal; the app stores only Stripe ids                                                                                            | By design                                |
| Information disclosure | Billing data seen by other roles or workspaces   | RLS: payments and invoices need `billing.manage`; balances need `billing.manage` or `documents.send`; event log is system-only                                                         | `billing.test.ts` (access rules)         |
| Denial of service      | Double spend, webhook retries, races             | Per-workspace advisory lock on credit movements; one hold per request; unique idempotency keys; each Stripe event processed once                                                       | `billing.test.ts` (race, replay)         |
| Elevation of privilege | Live money before release                        | Live Stripe keys are refused and live-mode events ignored; real sending needs both `production_signing` and `payments` flags                                                           | `billing.test.ts`, `stripe.ts`           |

## Phase 5: library, retrieval and retention

| Category               | Threat                                       | Control in place                                                                                                                                                                 | Test                                  |
| ---------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| Spoofing               | Someone retrieves another person's documents | 6-digit code emailed to the address, stored only as a hash, 10-minute expiry, 5 attempts; session token is random, hashed in the database, httpOnly cookie for 30 minutes        | `library.test.ts` (attempts, scoping) |
| Information disclosure | Probing which emails have documents          | Identical response whether or not documents exist; no code is sent when there are none. Response time can still differ by the email send; move sending to a queue to even it out | `library.test.ts`, `library.spec.ts`  |
| Information disclosure | Retrieval session reaching other requests    | RLS policies key on the session hash and match recipient email; only sent/in-progress/completed requests; files only when completed, not purged, and downloads allowed           | `library.test.ts`                     |
| Denial of service      | Code flooding                                | 5 codes per email and 30 per IP per hour, enforced in a database function                                                                                                        | `library.test.ts` (rate limit)        |
| Tampering              | Changed copy passed off as the signed one    | Every stored version has a SHA-256; downloads are checked; Check a copy compares fingerprints locally                                                                            | `library.spec.ts`                     |
| Repudiation            | Who viewed, downloaded, archived or deleted  | Audit rows for file views and downloads, archive, legal hold, retention changes and file deletion; guest downloads and link reissues go in the evidence log                      | `library.test.ts`                     |
| Elevation of privilege | Deleting records early                       | Retention deletion needs `workspace.manage`, an ended retention period, no legal hold, and the `retention_deletion` flag                                                         | `library.test.ts` (purge gating)      |

## Phase 6: team, contacts, templates and branding

| Category               | Threat                                                | Control in place                                                                                                                                                                                                              | Test                              |
| ---------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Elevation of privilege | A manager grants themselves or others more access     | `st_can_assign_role`: owner role only assignable by owners, and every permission of an assigned role must be one the caller holds. Custom roles can only contain permissions the editor holds. Members cannot edit themselves | `teams.test.ts` (role escalation) |
| Denial of service      | Workspace locked out by removing the last owner       | `st_keep_an_owner` trigger keeps at least one active owner                                                                                                                                                                    | `teams.test.ts`                   |
| Spoofing               | Someone else accepts an invitation                    | Token is random, stored only as a SHA-256 hash, expires, can be revoked; acceptance requires a verified account whose email matches the invitation                                                                            | `teams.test.ts`, `teams.spec.ts`  |
| Tampering              | Open redirect through the sign-in `next` parameter    | `safeNextPath` allows only `/invite/<token>`                                                                                                                                                                                  | Code review                       |
| Information disclosure | Private contacts seen by teammates                    | RLS: private contacts are visible only to their owner; shared contacts need `contacts.view`. A contact never grants access to any document                                                                                    | `teams.test.ts` (contacts)        |
| Tampering              | CSV export opened in a spreadsheet runs formulas      | Cells starting with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'`                                                                                                                                          | `teams.test.ts` (export)          |
| Tampering              | A published template changes under documents using it | Published versions are frozen by RLS (updates need `published_at is null`); edits go to a new draft version; documents record the template version they came from                                                             | `teams.test.ts` (templates)       |
| Information disclosure | Unshared templates seen by teammates                  | `st_can_view_template`: unshared templates are visible to their owner and to `templates.manage` holders only                                                                                                                  | `teams.test.ts`                   |
| Spoofing               | Customer branding imitating security or legal content | Brand appears only as a strip under the Signature Tender header and in the email header; disclosures, codes and signing controls keep standard styling. Colours must reach 4.5:1 contrast with white                          | `teams.spec.ts` (contrast)        |
| Tampering              | Uploaded logo used to serve active content            | PNG or JPEG only, checked by magic bytes, 512 KB cap, SHA-256 checked on read, served with `nosniff` and a sandboxing CSP                                                                                                     | `teams.test.ts` (branding)        |
| Repudiation            | Who changed roles, members, templates or branding     | Audit rows for invitations, acceptance, role and status changes, groups, custom roles, contact changes, template publish/archive/delete/use and branding                                                                      | `teams.test.ts`                   |

## Phase 7: API and webhooks

| Category               | Threat                                                   | Control in place                                                                                                                                                        | Test                               |
| ---------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Spoofing               | Stolen or guessed API key                                | 256-bit random keys, SHA-256 at rest, shown once; revoke, expiry, rotation; keys stop when the creator is suspended or removed                                          | `api.test.ts`                      |
| Elevation of privilege | Key used beyond its purpose                              | Scope check on every route; RLS still applies as the creating member, so a key never exceeds that member's role                                                         | `api.test.ts`, `api.spec.ts`       |
| Information disclosure | Key reaches another workspace its member belongs to      | Every route checks the document or request belongs to the key's workspace and answers 404 otherwise                                                                     | `api.test.ts` (workspace boundary) |
| Tampering              | Silent no-op when RLS hides a row from an update         | Updates that issue links check the row count and refuse                                                                                                                 | `api.test.ts` (embedded, remind)   |
| Denial of service      | Request floods, large bodies                             | Per-key per-minute limit in the database; streamed body limits for JSON and uploads                                                                                     | `api.test.ts` (rate limit)         |
| Tampering              | Retried client request acts twice                        | `Idempotency-Key` stores the first response for 24 hours; different body under the same key refused; 5xx frees the key                                                  | `api.test.ts`, `api.spec.ts`       |
| Spoofing               | Forged or replayed webhook at the customer               | HMAC-SHA256 over timestamp and body, event id header, documented 5-minute window and id de-duplication                                                                  | `api.test.ts` (signature)          |
| Information disclosure | Webhook secrets leaked from the database                 | AES-256-GCM with a key derived from a server secret that is not in the database; shown once                                                                             | `api.test.ts` (encryption)         |
| Elevation of privilege | SSRF through webhook URLs                                | HTTPS on port 443 only, no credentials, every resolved address must be public (checked at creation and before each delivery), redirects not followed, 10-second timeout | `api.test.ts` (SSRF, redirects)    |
| Information disclosure | Payloads carrying documents                              | Payloads hold ids, status, partner reference and recipient email only; files are fetched with `files:read`                                                              | `api.test.ts`                      |
| Repudiation            | Who created keys, endpoints, connections, embedded links | Audit rows for keys, endpoints, secret rotations, retries, connections; evidence events for embedded sessions and reminders                                             | `api.test.ts`                      |
| Spoofing               | Embedded signing link phished or framed                  | 15-minute link replacing the emailed one; frame-ancestors blocks framing so the address bar and security indicators stay visible                                        | `api.test.ts`, `csp.spec.ts`       |
| Elevation of privilege | Cron endpoint triggered by anyone                        | Requires `CRON_SECRET` bearer (constant-time compare); refuses when unset. It only moves outbox rows                                                                    | Code review                        |

| Category               | Threat                                            | Control in place                                                                                                                              | Test                                 |
| ---------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| Information disclosure | Reports reveal documents a member cannot see      | Report queries run under RLS as the member; credits and API sections need billing or developer permission                                     | `reports.test.ts`                    |
| Tampering              | CSV export runs formulas in a spreadsheet         | Every cell escaped (leading `= + - @` and control characters)                                                                                 | `reports.test.ts`                    |

| Information disclosure | Staff browse private customer documents           | Staff functions return counts, ids, names and hosts only; no files, titles of signed records or recipient emails                              | Code review                          |

| Elevation of privilege | SSRF through the Slack connector                  | Only `https://hooks.slack.com/services/...`, plus the existing public-address check before each delivery                                      | `reports.test.ts`                    |
| Information disclosure | Document details posted to a shared Slack channel | Messages carry title, event and a link that requires sign-in; never contents or emails. Slack URLs are masked in the app                      | `reports.test.ts`                    |

## Open items

- Staff accounts use the normal sign-in. Require passkey or 2FA for anyone in `platform_admins` before production.

- Webhook delivery checks DNS before sending, but the HTTP client resolves again (rebinding window). Route webhook traffic through an egress proxy that enforces public destinations before production.
- Webhook secret encryption falls back to `BETTER_AUTH_SECRET` when `WEBHOOK_SECRETS_KEY` is unset; set a separate key in production.

- `user` table readable by `st_app` (needed by auth). Mitigation planned: restricted view for member listings (Phase 6).
- Signer-side rate limiting is per recipient in the database; add IP-level limits at the edge (Vercel firewall) before production.
- Finalization runs inline after the last signature. Failures are retried by the daily job (Phase 9); a more frequent schedule needs a Pro plan.
- The billing system context is a session setting (`app.system_actor`) that any code using the app role could set. Only `@st/core` billing webhook functions use it; a dedicated database role for the webhook would make this a hard boundary before production.
- Invitation emails are sent after the database commit. If the process stops in between, the request shows as sent but nobody was emailed. Recipients can now get a new link at `/retrieve`, but an outbox worker would close the gap without their help.
- Secrets management: use Vercel/Neon encrypted environment variables; rotate `BETTER_AUTH_SECRET` per environment.
